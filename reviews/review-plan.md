# Adversarial Review: Gym Sales Tracker Implementation Plan

## Verdict

The plan is not implementation-ready. It jumps directly into coding despite the council report making the build conditional on validating the gym's need, checking the existing gym software, measuring the loss, establishing device/data ownership, and learning the worker's required entry format. Even if those gates pass, the planned implementation can silently lose sales, double-bill members, bind badges to the wrong people, and stop working offline because its scanner is loaded from a CDN.

The largest technical omission is that there is no explicit sale state machine or durable export workflow. A continuous camera feed, unrestricted item taps, and a loosely defined `exported` flag are not enough to guarantee one member, one intended purchase, and one worker charge.

## Findings

| Severity | Affected task | Finding | What goes wrong concretely | Specific recommendation |
|---|---|---|---|---|
| **High** | Missing prerequisite before Task 1 | **The required discovery/validation gate is absent.** The council report says to first ask the gym, identify the worker/owner pain, inspect the current software and retail/POS module, quantify the leak, and decide among existing POS, QR-to-phone form, or kiosk. | The project may spend a weekend replacing a process the owner does not consider broken, duplicate functionality the gym already pays for, or solve a $3/week loss with a device and ongoing support obligation. | Add a Task 0 with explicit go/no-go acceptance criteria: owner and transcribing worker agree to a trial; current software/POS capability is documented; several days of leakage are measured; kiosk is selected over built-in POS and QR form; a support owner and trial exit date are agreed. Do not begin implementation until it passes. |
| **High** | Missing prerequisite; Tasks 3–5 | **The badge data model is assumed rather than investigated.** The report explicitly calls out unknown barcode contents, whether physical-card and phone barcodes match, stability after reissue, and whether the identifier already maps to the gym's member record. | A card reissue can create a second identity, a phone barcode may decode differently, a family may share a badge, and the worker may be unable to find the typed name in the member software. Charges can land on the wrong account or become impossible to enter. | Before choosing enrollment, test representative physical cards and phone barcodes and document symbology, exact decoded value, stability/reissue behavior, shared-account behavior, and the gym software's canonical lookup key. Store a gym-recognized member identifier or require worker verification of mappings; define merge/remap/revoke flows. |
| **High** | Task 3; architecture | **The CDN scanner contradicts “self-contained” and “fully offline.”** The plan loads `html5-qrcode` via CDN but provides no vendoring or service-worker/cache task. A page previously loaded once is not a reliable offline installation contract. | After browser cache eviction, an iOS update, a hard refresh, or a CDN/network failure, the HTML opens but scanning does not. This is exactly the first-friction failure the council says will send workers back to paper. CDN updates can also change behavior without this project changing. | Pin a reviewed library version and serve the scanner code from the same origin. Add an explicit offline installation/cache strategy and an offline cold-start test after clearing ordinary browser cache and disabling network. If a true single file is mandatory, bundle the dependency into it; otherwise stop calling the artifact single-file and ship a versioned static bundle/PWA. |
| **High** | Tasks 3–5 | **No scan/tap state machine is defined, and the report's scanner-race mitigation is missing.** “Basic scan handler” and “push a sale” do not say when scanning stops, what events are ignored, or how the UI returns to idle. | Continuous decoding can fire the same badge repeatedly, replace the current member with a nearby badge while an item is being chosen, or carry a stale member into the next purchase. A fixed three-second delay alone still fails if the same badge remains in frame or selection takes longer. | Define and test an explicit state machine: `idle/scanning -> member-locked -> recording -> success -> idle`. Stop or pause the camera immediately on a valid scan, accept only one decode per session, freeze the member through submission, disable item controls outside `member-locked`, show a brief success state, then require badge removal or a deliberate reset before scanning again. Add the council's lockout as a secondary guard, not the only guard. |
| **High** | Task 5 | **Sale creation has no idempotency or double-tap protection.** The bracketed instruction only says to push a record into an array. | A member double-taps a lagging item button, Safari replays a handler, or two scan callbacks reach the sale handler; two indistinguishable records are stored and later both are billed. There is no safe way for the worker to tell an accidental duplicate from a quantity of two. | Generate a unique sale ID, disable all product buttons synchronously on the first accepted tap, make the transition one-shot, and record an explicit quantity. Provide a short, clearly visible undo/correction flow and flag suspicious same-member/same-item events within a small interval for worker review rather than silently deleting them. |
| **High** | Task 6 | **The export/double-billing workflow required by the report is not planned.** The council requires “since last pull,” an `exported` flag, and 30-day history; Task 6 only opens `window.print()`. | Every print can include old sales again, workers cannot know what was already keyed, and a reprint can cause duplicate charges. Conversely, marking records exported when the print dialog opens loses unbilled sales if the user cancels or printing fails. Browser print APIs provide no reliable “saved and keyed successfully” acknowledgement. | Add a staged batch workflow: create an immutable export batch with batch ID and included sale IDs; render/print that batch; leave it `pending`; require the worker to confirm **after keying** before marking it processed. Permit exact reprints with the same batch ID, corrections/audit entries, and 30-day processed history. Never infer completion from `window.print()` returning. |
| **High** | Tasks 4–5 | **Self-asserted name enrollment does not establish billing identity.** Any person can type any name; duplicate names, typos, prank enrollment, and shared family cards are expected rather than exceptional. The required “Not [Name]?” escape is omitted. | The first person to scan a badge can permanently bind it incorrectly. Later members see no correction path and sales accrue to the wrong account. A typed display name may not uniquely match a billing record. | Show the decoded/member identifier in a privacy-conscious form and require a second gym-recognized discriminator if available. Add “Not this member?”, remap, shared-card selection, and owner review tools. Keep submission disabled until a valid mapping exists, as the report requires. Prefer importing or staff-verifying a minimal badge-to-member mapping if the gym can supply one. |
| **High** | Architecture; Tasks 4–6 | **`localStorage` is treated as durable storage without a loss/recovery plan.** There is no handling for iOS eviction, private browsing, Clear Website Data, quota errors, malformed JSON, origin/URL changes, or device loss. | The kiosk can appear to work for days and then lose all pending sales and enrollments. A failed `setItem` may leave the UI showing success even though nothing persisted. Moving between hostnames or app/browser modes produces an apparently empty database. | Make persistence success a condition of the “done” screen: catch and surface quota/serialization failures and keep the transaction recoverable. Add schema/version validation, corruption handling, storage-health checks, and a visible pending-count reconciliation. Require encrypted/exported operational backups or a worker pull cadence acceptable to the owner; document that local-only storage is not guaranteed durable. For material revenue records, prefer IndexedDB plus tested backup/restore over one monolithic JSON value. |
| **High** | Missing prerequisite; architecture; Tasks 4–6 | **Device ownership, authorization to hold member data, and retention are unresolved.** The report explicitly asks whose iPad/Apple ID it is and whether storing names plus purchase history on a volunteer's personal device is permitted. | A personal device on a public counter exposes member purchase records to its owner, anyone holding the iPad, device backups/support workflows, and theft. The gym has no defined controller, retention policy, offboarding process, or incident response. | Make gym approval and a dedicated gym-managed device/account prerequisites. Minimize stored PII (prefer opaque member ID plus only the display information the worker needs), define retention and deletion rules, disable unrelated account features/notifications, use a device passcode and Guided Access/MDM where available, and document who may export, correct, back up, and erase data. Obtain the owner's explicit approval before collecting real member data. |
| **High** | Task 6; missing worker workflow | **The PDF schema is designed without observing the gym software's input screen.** This is an explicit blind spot in the report. | A readable chronological list can still force the worker to search, regroup, total quantities, translate product labels to SKUs, or resolve ambiguous names. The promised labor reduction may not exist, and transcription errors remain. | Observe one real re-keying session before implementation. Define and test report columns, grouping and sort order against the target screen (for example canonical member lookup key, display name, item/SKU, quantity, timestamp, sale ID, batch ID). Have the actual worker accept the report using representative data. Consider CSV only if the gym system supports import; do not assume PDF is optimal. |
| **Medium** | Task 5 | **Quantity is missing even though the stated flow requires item plus quantity.** The record shape contains one `item` and no `quantity`. | Buying two drinks requires repeated taps or repeat scans, which conflicts with double-tap suppression and makes intentional multiples indistinguishable from accidental duplicates. | Add an explicit, fast quantity interaction with a conservative default of one, an upper bound, and a single atomic sale record containing quantity. Test that the common one-item path remains scan → tap → done in under two seconds. |
| **Medium** | Task 5; product catalog | **Sales do not snapshot stable product data.** The proposed record only stores `item`, while catalog edits are made directly in code. | Renaming an item makes historical records ambiguous; two similar labels can map to the wrong product in the gym software; price or SKU changes cannot be reconstructed at billing time. Refreshes may also leave an old page and new catalog in use across tabs. | Give every catalog entry a stable ID and gym-software SKU, and snapshot ID, display name, price if relevant, and catalog version into each sale. Validate unique IDs/SKUs at startup and show the deployed catalog/app version in the owner view. |
| **Medium** | Tasks 4–6 | **The plan has no correction/audit workflow.** Enrollment, sale, and export records are append-only in concept, but real users will choose the wrong item, wrong quantity, or wrong name. | Without correction, the worker either knowingly bills a false record, informally edits browser storage, or ignores the kiosk. Direct deletion would destroy accountability and make batch totals impossible to reconcile. | Add owner-authorized void/correct operations that preserve the original record, reason, timestamp, and replacement link. Pending exports must reflect corrections; processed batches should receive explicit adjustment records rather than mutation. |
| **Medium** | Tasks 4–6; owner controls | **The public kiosk exposes member PII and administrative actions.** The plan has no privacy mode, session clearing, authorization boundary, or owner view. The council's hidden owner-only clear-data control is omitted—and “hidden” alone would not be authorization. | The next member can see the prior member's name or history, browse exports, print PII, remap identities, or erase all data. A discoverable clear button can destroy every pending charge; merely obscuring it does not secure it. | Return to a neutral screen immediately after success/timeout; never show history in kiosk mode. Put export, mapping corrections, history, and clear/reset behind an owner unlock (at minimum a non-default PIN with retry delay; preferably device-level managed access). Require typed destructive confirmation, a recent backup/export, and a warning showing the number of pending records before clearing. |
| **Medium** | Task 6 | **Exported PDFs create an additional unmanaged copy of member data.** The plan discusses local-only privacy as if printing preserves that property. | “Save as PDF” can leave files in Files/iCloud/Downloads, print previews, shared destinations, or a personal Apple account indefinitely. The system now has data outside `localStorage` with no retention or deletion path. | Decide whether printing to paper or saving a file is authorized, use the minimum identifying fields, include batch ID rather than unnecessary history, and document where exports may go and when they must be deleted/shredded. Test on the actual managed iPad/Apple ID configuration. |
| **Medium** | Tasks 1–3; missing deployment task | **HTTPS hosting is stated but not implemented or verified as an operational deployment.** There is no task for hosting configuration, pinning the origin, installation, permissions, certificate/network failure behavior, or update rollout. The report's “private GitHub Pages” suggestion is not validated in the plan. | The developer can pass a desktop test while the deployed iPad cannot grant camera access, cannot install reliably, changes origin and loses local data, or exposes the page publicly. Updating the page mid-shift can also create code/data-schema mismatches. | Add a deployment task using the actual chosen host and iPad: stable origin, HTTPS/camera permission, public-access threat assessment, versioned releases, rollback, schema migration, update procedure, and offline relaunch. Verify the exact privacy/access behavior of the selected host rather than assuming a private repository makes the published site private. |
| **Medium** | Tasks 1–3; missing kiosk setup | **The physical kiosk requirements are omitted.** The report requires Guided Access, Add to Home Screen/manifest, and continuous power; the plan contains none of them. | Members can navigate away, inspect admin/history screens, close the page, or encounter browser chrome and sleep/low-battery failures. Staff then inherit support work and fall back to paper. | Add a deployment checklist for a dedicated device: Guided Access configuration and recovery code owner, home-screen installation/manifest, auto-lock and screen/battery settings, secured long cable/stand, camera placement/focus tests, theft controls, and a one-page staff recovery runbook. |
| **Medium** | Task 3 verification | **Scanner testing is far too weak for the stated primary technical risk.** “Verify scan captures barcode string” does not cover the report's concern about iPad camera focus on phone-screen barcodes. | A desktop simulation passes while the real kiosk fails on glare, dim/cracked screens, physical badges, different barcode types, camera orientation, or repeated permission prompts. | Test on the exact iPad, enclosure, lighting, counter distance, and representative physical/phone badges. Record supported symbologies and time-to-scan targets, provide a manual fallback that does not permit arbitrary impersonation, and define what staff should do when camera permission or focus fails. |
| **Medium** | Tasks 5–6 | **Multiple tabs/windows can overwrite the monolithic sales array.** `read -> push -> setItem` is not transactional; two same-origin tabs or app/browser instances can read the same old array and each write a different result. Export and correction actions can race for the same reason. | One sale silently disappears, a sale enters an export batch while another context changes it, or one worker's processed flag overwrites another's new record. The `storage` event is notification, not locking. | Enforce a single active kiosk instance where possible and detect/warn on another active tab using a lease/BroadcastChannel. Use per-record IndexedDB transactions rather than rewriting one JSON array. Make export batch membership immutable and test cross-tab behavior explicitly. |
| **Low** | Tasks 5–6 | **Device time is accepted as authoritative without defining semantics.** | A wrong clock, timezone change, daylight-saving transition, or manual clock edit can put sales in the wrong pull window and reorder them, leading to missed or repeated entry. | Store UTC timestamps plus timezone offset, use sale IDs/batch membership—not time alone—to decide what is pending, and show a clock-health warning if time changes materially during a session. |
| **High** | Tasks 2–6 | **Every hard implementation problem is deferred to bracketed placeholders.** Product UI, scanner initialization/handler, enrollment, persistence, and report generation are all specified as `[Include ...]`, `[Implement ...]`, `[Logic ...]`, `[Add logic ...]`, or `[Use ...]`. | There are no acceptance criteria for validation, error handling, state transitions, accessibility, data schema, duplicate prevention, recovery, privacy, or export correctness. An implementer can satisfy the literal plan with the unsafe happy path described above. | Replace each placeholder with concrete behavior, invariants, data schemas, failure states, and executable tests. At minimum specify the scan state machine; enrollment/remap rules; atomic sale schema; quantity and duplicate handling; persistence failure behavior; export batch lifecycle; correction/history/retention rules; and real-iPad offline/deployment tests. |

## Minimum plan changes before implementation

1. Add a gated discovery task covering owner/worker validation, loss measurement, existing POS capability, barcode semantics, device ownership, privacy authorization, report schema, and a time-boxed side-by-side trial.
2. Replace the CDN/happy-path architecture with a version-pinned offline deployment, a transactional persistence design, explicit recovery behavior, and a tested scan-to-sale state machine.
3. Define identity enrollment and correction sufficiently to prevent wrong-member billing; typed names alone are not a billing key.
4. Define durable sale IDs, explicit quantity, product/SKU snapshots, one-shot submission, void/adjustment audit records, and privacy-safe kiosk/admin modes.
5. Treat export as a worker-confirmed batch lifecycle, not a print button, and retain/reprint processed batches without rebilling.
6. Add actual-iPad acceptance tests for offline cold start, physical and phone badges, double scans/taps, multiple tabs, storage failure, canceled print, data clearing, Guided Access, device restart, and recovery from a bad enrollment.

Until those changes are made, the plan does not meet its own claims of offline-first operation, accurate capture, lower worker effort, or safe handling of member data.
