# Round 1 findings

## High
- Item 4 only permits a five-second undo while `batchId === null`, so it does not implement the requested ability to void an accidental item while its batch is Pending. (Specify an admin correction flow that reloads the authoritative sale and batch, permits a persisted void only while the batch is Pending, keeps the sale in immutable batch membership but marks it VOID and excludes it from totals, and proves denial after processing and on failed saves.)
- Adding Member # and TYPED to the live report renderer changes every existing Processed batch's reprint, directly violating invariant 3; merely noting the change on the iPad does not preserve the invariant. (Version or snapshot report content at batch creation, retain a legacy renderer for pre-change batches, or make deployment conditional on proving there are no Processed batches before the trial.)
- The typed path accepts any value allowed by the very broad `BADGE_RE` and lets an unknown number self-enroll under any name, but the plan never makes the owner's required name-to-number match a mandatory pre-billing check. (Define a staff verification gate for every TYPED line, including mismatch handling that never bills or rebinds the claimed number, and put that workflow in the report, runbook, and device test.)
- Admin is excluded from inactivity handling even though opening admin leaves the state variable at `idle` and the scanner active, so a scan can interrupt administration and an unattended counter exposes batch confirmation and data clearing indefinitely. (Introduce an explicit `admin` state that pauses the scanner, ignores scans, resets an admin inactivity timer during legitimate work, and safely returns to idle with tests for scan isolation and timeout.)

## Medium
- The loss-window mitigation is prescribed despite staff acceptance and keying cadence remaining unanswered, and “midday” has no responsible role, trigger, completion check, or missed-run fallback, so the copy can simply never be made. (Make staff acceptance a pre-trial gate and specify who creates, prints, and shares each batch, the event-based cadence, how completion is recorded, and what happens when a checkpoint is missed.)
- The service-worker item does not specify precache/install failure behavior, navigation fallback for the exact installed GitHub Pages URL, cache version cleanup, or worker activation, so offline reopen or post-push freshness can still fail despite the stated network-first policy. (Define the complete service-worker lifecycle and scoped URL list, then test first install, exact home-screen launch offline, slow-network timeout, and an online update from version N to N+1 on the target iPad.)
- The device script undoes its only typed purchase before asking to create a batch containing Member # and TYPED, so either no batch can be created or a different test sale must be left in live data and risks being billed. (Define an isolated pre-trial test dataset and explicit cleanup or non-billing disposition, then verify the report with a retained typed sale before the production slate is established.)
- The plan calls for Playwright even though the stated dependency constraint allows only jsdom, leaving the offline acceptance test non-reproducible as written. (Use a documented manual real-browser test with no new dependency, or explicitly obtain approval to add a dev-only browser-test dependency and define how it is installed and run.)
- “Share to Mail” is treated as a second copy, but invoking the share sheet does not prove that a message was sent, received, or contains the complete batch. (Require receipt-side verification of the batch ID, line count, Member # and TYPED marker, and define print-only operation when Mail is unavailable.)

## Low
- The verification step says to force-reload after deployment without a deterministic build/version marker, so an unchanged-looking cached page can be mistaken for the new build. (Add a visible or admin-only release identifier and require matching it to the deployed commit before running trial checks.)
