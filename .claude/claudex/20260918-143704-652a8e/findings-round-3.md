# Round 3 findings

## High
- Rollback is not data-safe after v2 writes: the current/N-1 code neither excludes `voidedAt` sales nor preserves the v2 report semantics, so reverting can present a voided sale as chargeable and allow it to be confirmed. (Use a two-phase compatibility release that first teaches the rollback build to read/refuse newer data, declare that build the rollback floor, enable v2 writes only after it is proven on-device, and test a real rollback with v2 typed and voided sales.)
- The service-worker lifecycle cannot meet the claimed "one online reload" deployment check because no `skipWaiting()` or explicit activation flow is specified, `clients.claim()` does not replace JavaScript already running in an open client, and activation immediately deletes the last-known-good cache. (Specify an operator-visible update/activate/relaunch flow, retain and bound the N-1 shell cache, display page build plus controlling-worker/cache version, and rehearse both upgrade and rollback on the installed iPad while online and offline.)
- Round 2's whole-record multi-writer finding was dismissed without an adequate control: a stale Safari/PWA context can still overwrite newer sales or voids and the VOID-in-new-renderer rule does nothing when the stale client is the writer or confirmer. (Add a persisted revision/conflict check and a single-active-client lease or equivalent fail-closed guard, block mutations from builds below the data's minimum writer version, and test two-context interleavings for sale, batch, void, and confirm.)

## Medium
- Items 1–7, the report schema, and the new offline delivery layer are enabled in one release with no feature flags or canary sequence, so one defect affects the only production kiosk and forces an unsafe all-or-nothing rollback. (Stage separately deployable commits—compatibility/diagnostics first, state-machine fixes next, typed/void behind visible local flags, and the service worker last—and enable each only after its own on-device soak and rollback gate.)
- The proposed red age indicator watches only unbatched sales and only when admin is opened, so batching without successfully printing can make the risk signal disappear while the sole copy still remains on the iPad. (Track an explicit operator-verified paper-copy timestamp/status per Pending batch, alert in both kiosk and admin when either unbatched sales or an unverified Pending batch exceeds the checkpoint SLA, and give the runbook a named owner, tray check, escalation path, and missed-checkpoint recovery.)
- The plan exposes BUILD but no operational health for storage, cache/controller state, failed saves, pending-batch age, or last successful physical backup, leaving on-call staff unable to distinguish a safe offline kiosk from a stale or degraded one. (Add a compact admin health panel and runbook thresholds for build/worker/cache version, online/offline source, last save error, waiting and Pending counts/ages, last verified backup, and storage use, with explicit stop-selling/escalation actions.)
- Sales and processed batches accumulate indefinitely even though only 30 days are displayed, and there is no capacity estimate or near-quota/large-report soak test, so quota exhaustion or an oversized print could wedge purchases without warning. (Measure worst-case record growth, soak at and beyond the expected 30-day volume on iPad, warn before a conservative storage threshold, and specify a tested export-then-prune procedure limited to processed history while preserving the 30-day reprint invariant.)
